# Light v0.1.7 — переименование PainPatch

**В этой версии меняются названия, а не работа освещения.** Основано на v0.1.6, для которой пользователь сообщил о заметном восстановлении FPS.

- Для оригинального Painkiller: `dinput8.dll` + `Light.ini`. Имя `dinput8.dll` неизменно — так работает загрузка прокси DirectInput8.
- Для Custom EXE: `Light.dll` + `Light.ini`, загружать `LoadLibraryA("Light.dll")` и при необходимости вызывать `Light_Initialize` после появления `Engine.dll`.
- Диагностика записывается в `Light.log`, строки начинаются с `[Light]`.
- Старые `PainPatch.dll` и `PainPatch.ini` нужно удалить/заменить вручную: переименование не выполняется автоматически. Не загружайте одновременно старую и новую DLL.
- Для старого Custom EXE временно сохранён экспорт `PKPatch_Initialize` как совместимый псевдоним `Light_Initialize`.

# Light v0.1.7 — оптимизация обработчика света

**Тестовая версия, не игровой релиз.** Исправления нацелены на лишнюю CPU-нагрузку при вызовах `WorldMesh::Draw`. Освещение по-прежнему обновляется на каждом кадре; MinHook/экспорты/конфигурация устанавливаются **однократно**. После перестроения `Engine.dll`/смены D3D-устройства динамические данные могут обновляться, это не повторная установка хуков.

## Важное ограничение: PKMDL

Расширение перехватывает `WorldMesh`, но пока **не доказана работа на всех PKMDL**, особенно анимированных. Поддержка моделей, специальных материалов и конкретных шейдеров зависит от фактического пути их рендеринга. Подробности и тестовая матрица — в `KNOWN_LIMITATIONS.md`. Текущие `MaxRenderLightsPerMesh` и `MaxExtraPassesPerMesh` продолжают ограничивать реальную отрисовку даже при большом `MaxLights`.

## Быстрый запуск

1. Запустите `build-win32.bat` в консоли VS 2022. После успешной сборки `dist/vanilla` содержит прокси `dinput8.dll`, а `dist/custom-exe` — `Light.dll`.
2. **Сначала сделайте резервную копию** оригинальных DLL и INI. Установите только ОДИН из двух вариантов. Сборки для DX9, x86.
3. Настройки `Light.ini` считываются при запуске. Перезапустите игру при их изменении.
4. В логе ищите `[Light] Light v0.1.7 initializing` — это подтверждение обновления.
5. Проверяйте ту же сцену с душами и одинаковым расположением камеры. Сначала отключите логирование (`LogLights=0`).

## Что изменилось

- Признаки источников `Light` читаются/валидируются при `Entity::AddLight`, а не при каждом рендере связанного меша. При повторном `AddLight` данные обновляются.
- Для одного Uber-прохода (`FastSingleUberPass=1`) нет повторного поиска D3D9 и 4+4 обращений к render-state. Если освещение или состояния последующих объектов выглядят неверно, поставьте `FastSingleUberPass=0`.
- Положительный кэш D3D9 проверяется чтением одного указателя; при смене устройства производится новый поиск.
- Пустой реестр мгновенно пропускает сбор списка света, без mutex/hash lookup.
- Обычный запуск `LogLights=0` не обновляет многочисленные диагностические атомарные счётчики.
- Режим `TrustEnginePointers=1` позволяет обходиться без дорогих `VirtualQuery` в горячем пути. Для несовместимой `Engine.dll` или при подозрении на повреждённые указатели ставьте `0` (более медленные проверки).

## Рекомендуемый первичный профиль

```ini
[Settings]
UnlockLights=1
RenderExtraLights=1
MaxLights=16
MaxRenderLightsPerMesh=12
MaxExtraPassesPerMesh=4
FastSingleUberPass=1
TrustEnginePointers=1
LogLights=0
TimerSizeFix=1
```

ВНИМАНИЕ: `MaxLights=16` означает ёмкость очереди, а `MaxRenderLightsPerMesh=12` ограничивает количество обрабатываемого света на одном меше; `MaxExtraPassesPerMesh=4` ограничивает число вызовов отдельных световых проходов. Высокий FPS **не гарантирован**.

## Диагностика

Сделайте **два запуска в одной и той же сцене**:

- A: с `RenderExtraLights=0` (хуки/реестр включены, но дополнительные проходы отключены).
- B: с `RenderExtraLights=1` и указанным выше профилем.

Если A быстрый, а B медленный — проблема в стоимости рендера света или взаимодействии с DX9. Если A медленный — проблема в CPU-хуках или регистрации. Дополнительно можно временно использовать `LogLights=1`: диагностический лог теперь содержит `emptyRegistry`, `classOnAdd`, `singleUberFastPath`, `d3dCacheHits`, `d3dScans`. **Не сравнивайте FPS** с включённым логированием, потому что диагностика добавляет накладные расходы.

Ни один из новых методов не делает рендер света «однократным»: динамические источники меняют положение и видимость, поэтому обработка продолжается по кадрам. Оптимизация убирает лишние проверки/выделения/переинициализации, а не сами light passes.

## Обратная совместимость / ограничения

Один `RenderUberLightPass` теперь может влиять на последующие D3D-состояния, если движок не восстанавливает их сам. При артефактах попробуйте `FastSingleUberPass=0`. `TrustEnginePointers=1` допустим только для достоверных указателей и ожидаемой структуры `WorldMesh`/`Light`, полученных из движка. Эти структуры необходимо проверять на каждой ветке `Engine.dll`.

Пока не проведены реальная MSVC-сборка этой версии и тест FPS в Painkiller. `ctest` ядра прошёл; C++ Windows-хуков синтаксически проверен с заглушками WinAPI. **Не заменяйте рабочую сборку без бэкапа.**

## Комплектация

- `dinput8.dll`: прокси DirectInput8 для оригинального EXE; после загрузки ждёт Engine.dll и устанавливает хуки.
- `Light.dll`: то же расширение без зависимости от имени `dinput8.dll`, для явной загрузки из Custom EXE. Экспорт `Light_Initialize` следует вызывать после загрузки Engine.dll.
- `Light.ini`: максимальное число источников света, таймер, хуки D3D9, диагностика.
- Рендер: `AddLight/ResetLights`, `WorldMesh::Draw`, `RenderLightPass`, `RenderUberLightPass`; группы по 3/4 источника; при наличии поддерживаемого устройства D3D9 — аддитивные проходы.
- Исправление таймера RDTSC (если экспорт присутствует).

## Сборка

На Windows 10/11 установите Visual Studio 2022 с Desktop development with C++ и CMake. Запустите в командной строке в папке проекта:

```bat
build-win32.bat
```

Нужен Интернет: CMake автоматически скачивает [MinHook](https://github.com/TsudaKageyu/minhook) (BSD). После успешной сборки находятся `dist/vanilla/dinput8.dll` и `dist/custom-exe/Light.dll`. Также есть `.github/workflows/build.yml`: загрузите исходники на GitHub и запустите Actions → Build Windows x86 patch → Run workflow. Артефакт должен содержать оба варианта.

## Проверка

1. Сделайте копию игры. Не устанавливайте поверх уже существующего `dinput8.dll` другого мода.
2. Для оригинала поместите DLL и INI из `dist/vanilla` рядом с EXE. Для своего EXE используйте `dist/custom-exe` и `LoadLibraryA("Light.dll")`, затем `GetProcAddress(...,"Light_Initialize")`.
3. Убедитесь по `Light.log`, что хуки установлены и освещение активно.
4. Начните с `MaxLights=8`, проверьте отрисовку 5–8 источников, затем поднимайте до 16/32/128.
5. Если появляются артефакты, поставьте `HookD3DState=0`, затем `UnlockLights=0`; при сбое удалите DLL.

**Пока отсутствуют:** PNG-скриншоты, вывод `Game:Print()`, надпись версии и патч границ оконного режима, присутствующие в оригинальном erychpatch. DX11 также не поддерживается. Сначала важно подтвердить работу светового рендеринга в DX9 на конкретных сборках Engine.dll.

Исходники самостоятельной реализации публикуются под MIT. Оригинальную DLL и декомпилированный исходный код стороннего автора пакет не содержит.

## Исправление v0.1.1 (ошибка LNK2001)

В `.def` исправлен экспорт `Light_Initialize`. В x86 MSVC строка
`PKPatch_Initialize = _PKPatch_Initialize` заставляла линковщик искать
неправильное внутреннее имя. Теперь используется `Light_Initialize`
без алиаса. Изменены `src/dinput8.def` и `src/Light.def`.

Для сборки запустите `build-win32.bat`. Если остался кэш старой сборки,
удалите папку `build` и запустите скрипт повторно.

Это исправление **только ошибки линковки**; работоспособность света
в оригинальной игре и Custom EXE ещё требует проверки.


## Диагностика v0.1.3 (свет от душ не появляется)

Этот релиз **не заявляет полное исправление света**. В v0.1.2 лог ACTIVE означал только успешную установку хуков, а не факт рендеринга. В 0.1.3 добавлены периодические агрегированные счётчики `DIAG`, в том числе при пустом списке света.

1. Временно уберите другие моды, использующие `dinput8.dll`, сохраните резервную копию игры.
2. В `Light.ini` оставьте `UnlockLights=1`, `LogLights=1`, `PreserveNativePasses=0`, `SafeNativeFallback=1`, `MaxLights=16`.
3. Запустите сцену с несколькими душами, дождитесь 5–10 сек., приложите три строки с префиксом `DIAG` из `Light.log`.
4. Если `Add=0`, значит `Entity::AddLight` не вызывается в тестовой сцене (или вызовы используют другой путь). Если `DrawFlag=0`, то проход `0x40000000` не приходит. Если `nonempty=0` при `Add>0`, нужно проверить ключи `Entity*` vs `WorldMesh*`, стадию Reset или мимоходные вызовы. Если `accepted=0` при `nonempty>0`, проблема в фильтрации. Если `uberCalls=0` при `accepted>0`, смотрим fallback к одиночным проходам и обнаружение D3D9.
5. Для проверки, выключает ли наш hookDraw штатный свет, повторите ту же сцену с `PreserveNativePasses=1` и сравните. **Это только диагностический режим:** при работающих дополнительных проходах возможно двойное освещение.
6. Отдельно сравните `UnlockLights=0` и `UnlockLights=1` в одинаковой сцене. **Не следует объявлять патч рабочим только по успешному установлению хуков.**

В диагностике `totalSeen`, `accepted`, `singleCalls`, `uberCalls` — накопительные счётчики за игру, а `tracked` — текущие сущности в реестре, `maxSnapshot` — наибольшее количество источников на одном меше. `SafeNativeFallback=1` снижает риск исчезновения штатного света из-за пустого реестра. Любые неизвестные ABI/смещения всё равно следует подтверждать на конкретной сборке Engine.dll.

## v0.1.4 — проверка падения FPS

**Экспериментальная сборка, не подтверждена внутри игры**. Основана на 0.1.3 с:

- Кэшем поиска D3D9-устройства для обычного стабильного RenderDevice; повторный поиск при изменении.
- Одним снимком списка света на вызов WorldMesh::Draw вместо двух.
- Ограничителями MaxRenderLightsPerMesh (по умолчанию 12) и MaxExtraPassesPerMesh (4). Очередь регистрации настраивается MaxLights (16 в диагностическом профиле).
- RenderExtraLights=0 сохраняет родные проходы (без suppression), но оставляет хуки и DIAG для A/B теста.
- Добавлены DIAG perf counters: cappedLights, cappedPasses, passthroughDraws.

**Порядок проверки**: на копии игры в одной сцене измерьте FPS по 10–15 секунд при (а) `UnlockLights=0, TimerSizeFix=0`; (б) `UnlockLights=1, RenderExtraLights=0, TimerSizeFix=0`; (в) `UnlockLights=1, RenderExtraLights=1, MaxRenderLightsPerMesh=8, MaxExtraPassesPerMesh=2, TimerSizeFix=0`; только если (в) работает, повышайте бюджет. При любом лаге/артефактах возвращайте `UnlockLights=0`. Данные счётчиков отправьте вместе с FPS. Если (а) медленно, проблема может быть не в патче света; если (б) медленно, профилируйте хуки/реестр; если только (в), стоимость именно дополнительных световых проходов или работы с D3D9.


## Экспериментальная v0.1.5: диагностика 11–16 FPS

Собери `build-win32.bat`. Для чистоты теста на одной и той же сцене с душами запускай игру заново между тремя режимами (заменяй строки в `dist\vanilla\Light.ini` **после копирования** файлов в каталог игры):

1. **Без хуков**: `UnlockLights=0`, `TimerSizeFix=0`, `LogLights=0`. Это контрольная производительность без расширения света. Если игра всё равно медленная, исследовать игру, мод, другие хуки и D3Dev.
2. **Хуки без дополнительных проходов**: `UnlockLights=1`, `RenderExtraLights=0`, `TimerSizeFix=0`, `LogLights=0`. Если здесь резко падает FPS, проблема в цене хуков, регистрации или конфликте модификаций, а не в освещении GPU.
3. **Один проход**: `UnlockLights=1`, `RenderExtraLights=1`, `MaxLights=8`, `MaxRenderLightsPerMesh=4`, `MaxExtraPassesPerMesh=1`, `TimerSizeFix=0`, `LogLights=0`. Если только этот режим медленный, исследовать вызовы `RenderLightPass`/`RenderUberLightPass` и совместимость D3D9.

После FPS-тестов в третьем режиме включи `LogLights=1`, подожди хотя бы пять секунд и скопируй строки `DIAG` из `Light.log`. Особое внимание: `nonempty`, `maxSnapshot`, `deviceMissing`, `d3dScans`, `d3dNegativeCacheSkips`, `uberCalls`, `singleCalls`. Это **накопленные счётчики**, не значения за один кадр.

Никогда не запускай одновременно две DLL, которые перехватывают те же методы освещения. Проверь также, нет ли уже установленного оригинального erychpatch в используемом моде.

Это экспериментальный исходный код. В лабораторных проверках успешно прошли тесты ядра и синтаксис Windows-части с заглушками, но производительность и визуальное освещение в реальной игре не подтверждены.
