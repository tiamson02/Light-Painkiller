# Проверка производительности Light 0.2.4

Сначала измерить FPS в одном и том же месте с одинаковым разрешением и видом камеры, одинаковой погодой/эффектами, без вертикальной синхронизации и ограничения FPS. Повторить после прогрева шейдеров и текстур. Для каждого варианта полностью закрыть игру.

| Профиль | UnlockLights | ExtraPassesPerMesh | TimerSizeFix | Что проверяет |
|---|---:|---:|---:|---|
| A: без DLL | — | — | — | Фактическая стоимость десятков CLight для самого движка |
| B: загружена, хуков нет | 0 | 0 | 0 | Издержки загрузки прокси без перехватов |
| C: только таймер | 0 | 0 | 1 | Стоимость TimerSizeFix |
| D: свет 1 проход | 1 | 1 | 0 | Световые хуки и один дополнительный проход |
| E: свет 2 прохода | 1 | 2 | 0 | Стандартная настройка Light без таймера |

Если FPS падает уже в профиле A, сравнить объекты уровня (количество активных ламп, дальность света и перекрытие мешей). Ни одна DLL не гарантирует 1000–2000 FPS при произвольном числе динамических источников.

В профиле E можно на короткое время включить `LogLights=1` (сам сбор счётчиков и периодический вывод тоже имеют цену). В `Light.log` появится строка `DIAG` с накопительными счётчиками:

- `add`, `reset`, `draw`: вызовы перехватов движка;
- `overflowEligible`: меши с 5+ зарегистрированными источниками, для которых Light готовит расширение;
- `extraSingles`: дополнительные вызовы RenderLightPass; `extraUberLights` и `extraUberBatches`: Uber-лампы и число соответствующих проходов;
- `stockOnly`, `unsafeSkipped`, `incompleteNative`, `skippedUnsupported`, `skippedNoDevice`: почему расширение не произошло;
- `timerCalls`: обращения к исправленному таймеру;
- `trackedEntities`: количество активных записей в реестре.

Сравнивать приращения счётчиков между соседними строками `DIAG` (каждые ~5 секунд), а не абсолютные значения с момента запуска.

Диагностика без исходников игры не показывает GPU frametime. Если FPS проседает пропорционально `extraInDraw`, следующий шаг — профилирование оригинальных RenderLightPass/RenderUberLightPass в совместимом D3D9 анализаторе и адаптивный выбор света по площади/влиянию, а не произвольное повышение лимита проходов.

## Дополнительная диагностика v0.2.4

`lightCacheHit` показывает число повторных регистраций валидного Light* за 16 мс, при которых удалось пропустить `VirtualQuery`.
`lightCacheMiss` — число полных проверок памяти Light* при классификации. Эти счётчики включены **только** при `LogLights=1`.

Производительность реестра C++ не эквивалентна FPS в PainEditor. Реальную стоимость сцен с душами, прозрачными частицами, bloom и дополнительными световыми проходами нужно оценивать по A/B-тестам в одной сцене:

1. Полностью без `dinput8.dll` / `Light.dll`, если возможен такой запуск.
2. `UnlockLights=0`, `TimerSizeFix=0` — загрузчик без перехватчиков.
3. `UnlockLights=1`, `ExtraPassesPerMesh=0`, `TimerSizeFix=0` — ноль световых хуков, тот же baseline.
4. `UnlockLights=1`, `ExtraPassesPerMesh=1`, `TimerSizeFix=0`.
5. `UnlockLights=1`, `ExtraPassesPerMesh=2`, `TimerSizeFix=0`.

Сначала сравни FPS без диагностики (`LogLights=0`); отдельный короткий прогон с `LogLights=1` нужен для `extraSingles`, `extraUberBatches`, `skippedUnsupported`, `skippedNoDevice`, `overflowEligible`, `lightCacheHit`, `lightCacheMiss`. Высокий `extraSingles` или `extraUberBatches` может означать GPU/fillrate затраты, которые не уменьшаются ускорением реестра. Отсутствие разницы между нулевыми хуками и активной DLL означает, что необходимо профилировать штатный рендер, частицы и геометрию, а не увеличивать оптимизации хуков наугад.
